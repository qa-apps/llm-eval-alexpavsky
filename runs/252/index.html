Based on the provided context, the best practices for test data isolation in Playwright include:

1. **Two-layer isolation strategy**:
   - **Layer 1 — Dynamic API-driven seeding**: Create unique workspaces, users, and contexts for each test suite using REST/GraphQL. Append a cryptographic seed or timestamp to every name to prevent record collisions.
   - **Layer 2 — Isolated browser context pooling**: Ensure each Playwright worker runs in its own browser context to avoid state leaks between parallel tests.

2. **Cleanup contract**: Every fixture that creates state should register a teardown, preferably using Playwright's `auto` fixture pattern to ensure cleanup occurs even on test failure. Use API DELETE methods for teardown to maintain speed.

3. **Code example**:
```ts
test.beforeEach(async ({ request }, testInfo) => {
  const seed = `${testInfo.title.replace(/\W/g, '-')}-${Date.now()}`;
  const workspace = await request.post('/api/workspaces', { data: { name: seed } });
  testInfo.attach('workspace', { body: JSON.stringify(workspace) });
  return async () => request.delete(`/api/workspaces/${workspace.id}`);
});
```

4. **Trade-offs**: Consider the pros and cons of different methods like static tenant mapping, dynamic API seed, and DB snapshots, and choose the best use case for each.

5. **Evidence retention**: Retain traces for failures and first retries in CI to ensure reliable evidence about release risk.

These practices help in reducing flakiness, ensuring reliable test execution, and maintaining a clean state between tests.

Prompt

What are the main categories of prompt injection attacks that QA should test for?

Chatbot answer

**Main prompt‑injection categories that a QA team should cover**

| Category | What the attacker does | Typical impact |
|----------|------------------------|----------------|
| **Direct injection** | The user’s text explicitly tells the model to “ignore previous instructions” or to reveal the system prompt. | System‑prompt / policy leakage, policy override. |
| **Indirect injection – retrieved content** | Malicious instructions are hidden in a third‑party document (PDF, web page, email, etc.) that the agent reads as part of its retrieval step. | Unauthorized actions, data exfiltration, tool‑call hijack. |
| **Indirect injection – uploaded file** | The payload is placed in a user‑uploaded `.txt`, `.pdf`, `.docx`, image alt‑text, etc., which the chatbot parses. | Same as retrieved‑content injection but bypasses plain‑chat filters. |
| **Data‑extraction / secret‑leakage** | Role‑play or reverse‑psychology prompts coax the model to reveal training data, PII, API keys, or other secrets. | Information‑disclosure risk. |
| **Tool‑call hijack** | Crafted input causes an agentic system to invoke a downstream tool with attacker‑controlled arguments (e.g., sending money, deleting data). | Unauthorized tool usage, financial or data loss. |
| **Crescendo / multi‑turn (state) attacks** | Each turn looks benign, but a sequence of turns builds up to an unsafe request that succeeds once the conversation state is accumulated. | Refusals at early turns collapse at the final turn. |
| **Dual‑use safety framing** | The harmful request is framed as a “what‑not‑to‑do” or safety‑check question, tricking the model into enumerating dangerous information. | Indirect leakage of prohibited content. |
| **Encoded / homoglyph attacks** | Payload is hidden using base64, ROT13, Morse code, zero‑width characters, Cyrillic look‑alikes, etc., to bypass simple substring filters. | Same impact as direct injection but harder to detect. |

These categories capture the breadth of prompt‑injection techniques that QA should include in an adversarial test suite (e.g., Promptfoo, DeepEval) and verify both single‑turn and multi‑turn behaviours.
