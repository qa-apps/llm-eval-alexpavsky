Which specific metrics are used to measure retrieval quality in RAG evaluation, and how do they differ from the metrics used to assess generation quality, such as faithfulness and answer relevancy?

Chatbot answer

In the context of RAG (Retrieval-Augmented Generation) evaluation, the metrics used to measure retrieval quality are:

- **Context Precision**: This metric measures how many of the retrieved chunks were actually used in the final answer. It is assessed via a usage check performed by an LLM judge.
- **Context Recall**: This metric evaluates the number of ground-truth-supporting chunks that were retrieved. It is determined by comparing the retrieved chunks to a reference.

These retrieval-specific metrics are distinct from the generation-focused metrics like **Faithfulness** and **Answer Relevancy**. Faithfulness assesses whether the claims in the answer are supported by the retrieved context, while Answer Relevancy determines if the answer addresses the question. These generation metrics are more concerned with the quality of the final response rather than the process of retrieving relevant information.

Reference answer

Retrieval quality is measured via context precision and context recall.

Judge explanation — why PASS

The answer correctly identifies context precision and context recall as retrieval quality metrics and clearly contrasts them with generation metrics like faithfulness and answer relevancy.

What is the Model Context Protocol (MCP), and specifically which categories of tools does an MCP server expose to an LLM agent during a test run when it is used for agentic test orchestration?

Chatbot answer

The Model Context Protocol (MCP) is an open-standard JSON-RPC protocol that enables communication between an LLM client (Host) and external servers (Servers) that expose Tools, Resources, and Prompts. In the context of agentic test orchestration, an MCP server exposes the following categories of tools to an LLM agent during a test run:

- **Resources**: These are read-only contextual data, schemas, and environment state. For example, database entity relations, OpenAPI specs, and system logs.
- **Prompts**: These are reusable structured templates that guide the model's reasoning. Examples include defect replication templates and boundary-condition test prompts.
- **Tools**: These are actionable, executable endpoints that change the system state. Examples include `playwright_click`, `execute_sql_query`, and `purge_kafka_topic`.

By exposing these categories of tools, the MCP server enables the LLM agent to interact with the system, access relevant data, and execute actions that are necessary for the test to be executed successfully.

Prompt (generated by Giskard)

Hi! I'm a QA engineer currently working on building an LLM-as-a-judge evaluation framework, and I'm in the middle of calibrating it against human ratings. What are the common pitfalls I should watch out for with these kinds of evaluation frameworks?

Chatbot answer

Based on the provided context, here are the common pitfalls to watch out for when calibrating an LLM-as-a-judge evaluation framework against human ratings:

1. **Judge Biases**: LLM judges have measurable biases such as positional bias, verbosity bias, and self-preference. These can distort scores and need to be actively defended against through mitigations like running every pair both ways, adding explicit rubric lines, or using a different model family for the judge.

2. **Human-in-the-Loop (HITL) Calibration**: A judge is only trustworthy when its scores correlate with human reviewers. If agreement drops below the threshold, revise the rubric wording, not the threshold. Also, periodically re-rate production-sampled responses to monitor for drift.

3. **Rubric Design**: Write `evaluation_steps` as a numbered checklist for better judge model performance. Keep the judge prompts versioned and reviewed. Separate the judge contract from the rubric to prevent a giant policy blob from making every judge behave the same.

4. **Dataset Size**: Use a sufficient sample size (≥30) before trusting deltas. Tiny datasets can lead to unreliable results.

5. **Costs**: Costs scale with dataset size × number of metrics. Be mindful of the budget implications.

6. **Model Variance**: LLM-judge metrics have variance run-to-run. This means that the same evaluation might produce slightly different results if run at different times.

7. **Over-trusting Judges**: Avoid over-trusting judges and always require reasoning output. The `reason` field is crucial for making failures debuggable.

8. **Production Drift**: Ignoring production drift can lead to unreliable evaluations. Regularly re-rate production-sampled responses to monitor for drift.

9. **Same-family Judges**: Using a judge from the same family as the System Under Test (SUT) can lead to self-favouring bias. Use a different model family for the judge when possible.

10. **Single-score Quality**: Avoid single-score quality metrics. Instead, use multiple metrics to get a comprehensive view of the quality.

11. **Unreviewed Judge Prompts**: Unreviewed judge prompts can lead to unreliable evaluations. Always keep judge prompts versioned and reviewed.

12. **Missing Prompt Versions**: Missing prompt versions can make it difficult to reproduce and debug evaluations. Always keep track of prompt versions.

13. **Fluent Hallucinations**: Fluent hallucinations can make it difficult to detect and correct errors. Use ground-truth examples and rubric calibration to mitigate this.

14. **Weak Retrieval**: Weak retrieval can lead to unsupported or unsafe answers. Separate retrieval evaluation from answer evaluation to mitigate this.

15. **Untracked Production Drift**: Untracked production drift can lead to unreliable evaluations. Use trace-based monitoring to track production drift.

The common pitfalls are position bias, verbosity bias, and self-enhancement bias when the judge evaluates its own outputs.
