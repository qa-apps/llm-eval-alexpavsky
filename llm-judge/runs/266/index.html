How do we build the right safety guardrails? If Argon can help defenders find complex software bugs or help scientists design experiments, how do we stop bad actors from using it to launch cyberattacks or create biological threats? (Misuse)
Can we trust the model to do the job the right way? As models become more resourceful problem-solvers, how do we make sure they don’t cut corners, cross boundaries, or make incorrect high-stakes decisions? (Misalignment and Prompt Injection)

Misuse prevention across high-risk domains

In biology evaluations, unguarded versions of the model also showed a much stronger ability to help troubleshoot complex lab procedures step by step. Following our Frontier Safety Framework, since we saw elevated capabilities in the cyber and biological domains, we put our next-generation set of frontier safeguards in place across both areas.

On an adversarial set meant to stress test the model, violations reduced nearly twofold — also significantly better than previous Gemini models. Second, we wrap the model in three layers of real-time protection; this is to prevent determined attackers that might try to jailbreak (i.e. trick) the model by disguising a dangerous request as a harmless story or breaking it into dozens of small questions over several weeks. Here is how these protections work:

Input screening: Smaller models check incoming requests and conversation context for malicious intent or dangerous requests.
Internal introspection: Even if a request is cleverly disguised to look harmless, small transformers ("activation probes") read the model’s internal neural signals and are trained to spot when it is activating knowledge about cyberattacks or biological threats.
Continuous monitoring: As the model reasons and writes its response across multiple steps, we combine these signals and take action when necessary such as cutting off the agent mid-stream if the responses become problematic.

There is a race condition hiding in your flaky test
Patrick Eaton
October 14, 2026
4 min read

A test fails. You rerun it. It passes. You move on, blaming an under-provisioned staging environment, drifted test data, or a timing issue. But a lot of ‘timing issues’ are race conditions, a problem computer science named and studied decades ago. Once you call it that, you can go find the root cause.

We put a small set of tests in front of every pull request as a merge gate, so one red test blocks the merge, which makes small failure rates add up fast. If each test passes 99% of runs, a 17-test gate fails about 16% of the time, so three out of every 20 pull requests would fail for no reason. Add higher development velocity, and developers hit these false failures daily. They stop investigating and blindly rerun the test.

So we stopped allowing reruns and investigated every failure. That took a couple of months. Each failure turned out to be something specific, and a lot of them were the same thing: an assumption about order that nothing enforced.

The trap of unenforced order


We constantly assume sequential order in our code. We expect a component to read a cache only after a previous component updates it, or a UI element to be clickable only after its data loads.

Independent systems run at their own pace. Database queries take varying times depending on load. Writes aren't instantly visible, and network requests interleave unexpectedly. When code relies on which operation finishes first without explicitly enforcing it, it works until the race goes the other way.

A flaky test is a sampling machine aimed at exactly the places where your software assumes an ordering it never enforces, running enough trials to turn a rare interleaving into a reproducible rate. A user might see a glitch once every few months and refresh the page, but an automated suite running hundreds of times a day catches it constantly. More runs make flakiness more expensive, and give you enough samples to find what’s behind it.

The stale cache race

One of our tests occasionally returned a blank account name right after setting it. We assumed a linear process: the write commits, the cache clears, and the next reader hits the database to cache the new record.

What actually happened:

The application issues a write inside an open transaction, making it invisible to other readers.
The cache entry clears before the transaction closes.
A second reader arrives in that gap. It finds no cache, reads the database, and gets the old record because the new one hasn't committed yet.
The reader populates the cache with the old data.
The write transaction commits.


The cache now holds pre-write data until the entry expires. Someone sets an account name, reads it back blank, and keeps reading it blank long after the write succeeded. Waiting wouldn’t have fixed that test.

The dead click

Another test clicked a credential but intermittently failed to load the details page. We assumed the click would hold the old page briefly, fetch the new data, and render the new UI.

The data arrived in 287 milliseconds. Then the new page needed translation files the list page had never loaded. The transition had no fallback for that wait, so the app stayed on the list page for 17 seconds with no spinner and no error. The click only succeeded if the test arrived via a path that happened to pre-load those specific translation files into memory.

Who owns the assumption?

A race condition means somebody assumed an ordering that was never guaranteed. Sometimes the application assumes it, and sometimes the test assumes it.
When our suite's flake rate jumped 6% in a single week, we found two tests sharing a hardcoded record name, each assuming it would get there first.

What Is A Remote MCP Server?

A remote MCP server runs on a host outside your computer and accepts MCP requests over HTTP. An AI assistant connects to it by URL instead of a local process. A local MCP server starts as a process on your computer. Every user installs it and keeps a token in a config file. A remote MCP server, also called a hosted MCP server, runs on the vendor side, so a browser assistant connects to it by URL and a login. The protocol basics are covered in the post on building a Python MCP server.

What Is Testomat.io MCP Server?

The Testomat.io MCP server is a hosted version of the open source MCP server. Each project has its own URL, and any assistant connects to it: a web chat with a login, an IDE with a config from the project page. The same prompt works in every client. The full capability list is on the MCP page, and the release notes are in the changelog entry.

How To Connect Your AI Assistant

The project has a page for this. You open the project and choose MCP Server under Extra in the top-right corner. The page shows the project URL and ready configs for popular clients, and you copy the entry for your assistant. The token is part of the config, so the API settings stay closed.

claude.ai and ChatGPT: add the project URL as a custom connector in the assistant settings and approve access on the Testomat.io login page. ChatGPT needs Developer mode in the Advanced part of its Connectors settings, and custom connectors are available on paid plans.
Cursor, Claude Code, VS Code and other IDE clients: paste the config from the MCP page into the client.
Self-hosted Testomat.io: use the local config from the same page. The docs tutorial covers the details.

The connection uses the permissions of the person who connected it, and the project history records every change from the assistant. The quickest check is a question: you can ask the assistant to list your test suites, and real suite names confirm the link.
