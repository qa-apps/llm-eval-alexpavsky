Today, we’re launching “Polar Peaks”, our third quest in the AI Quests series, created by Google Research and the Stanford Accelerator for Learning to teach students how AI works and how to use it responsibly. AI Quests invites students ages 11 to 14 to step into the shoes of Google researchers to tackle some of humanity’s biggest challenges.

More than 400,000 quests have been completed to date, localized to 10 languages. Alongside the new quest, we’re also releasing training modules for teachers.

Polar Peaks: A journey to map the human brain

In the first two quests, students tackle flood forecasting and eye disease detection, inspired by Google Research’s Flood Forecasting initiative and AI model for diabetic retinopathy screening. Our newest quest, “Polar Peaks,” has students travel to the frontiers of neuroscience and see how AI can speed up scientific research.

With the guidance of in-game mentors, students scan and map the neurons in the brain to better understand the game character’s memory loss. They complete tasks like data cleaning and model testing, learning firsthand that AI requires careful human oversight and critical thinking.

The quest is inspired by over a decade of our research in connectomics: the science of mapping neural networks in the brain. Upon completion of the quest, students hear from two researchers behind our real-world breakthroughs, including the recent mapping of the complete fruit fly brain, the largest brain map by number of neurons to date.

Training modules: Tools for teaching AI literacy

Teachers play a critical role in bringing the quests to life and fitting them into their existing classroom curriculum. We’re rolling out new dedicated teacher training modules to help educators reinforce key AI literacy concepts and use AI Quests for learning and discussion. These are launching within the Google AI Educator Series. The modules for Quest #1 and #2 are accessible here. The training module for Quest #3 will follow next month.

Earlier this year, AI Quests won a 2026 Webby Award for AI Education, Learning & Training, and Best Global K–12 Learning Solution at the ETIH Innovation Awards. We’ll continue working with educators and partners to bring more quests to more classrooms this school year.

How to choose the right Cypress plugins for your project
November 2, 2026
16 min read

You need your tests to do something Cypress doesn’t do on its own, such as waiting for a sign-up email or comparing a screenshot against an approved baseline. A search turns up several plugins that claim to handle it, and integrating the plugin only takes a few minutes. Finding out you integrated the wrong one takes longer, because the problems rarely show up on the day you install it. They show up when a CI job ignores your tag filter and runs the whole suite, or when the plugin blocks your next Cypress upgrade, or when Cypress runs slower until you disable that one plugin.

Integrating a plugin only takes a few minutes. Finding out you integrated the wrong one takes longer.

A Cypress plugin is a package that adds functionality to your Cypress test suite: custom commands, a preprocessor, visual or accessibility checks, a CI integration, or a reporter. Most are npm packages that you install and update separately from Cypress, so each one is a dependency your team maintains. Cypress doesn’t formally review vendor or community plugins, so you decide what goes into your suite.

The Cypress plugin directory helps with that choice. It groups official, vendor, and community plugins by where they fit in your test suite, and each card shows who maintains the plugin, when it last published, and which Cypress versions it declares support for. Those signals, plus a few questions about your own project, tell you whether a plugin belongs in your suite before you install it.

Not every entry in the directory is an npm plugin. Its AI tooling category lists Cypress AI Skills, which help AI coding assistants write, explain, and fix Cypress tests, and the Cloud MCP server, which gives those assistants your Cypress Cloud test data. The directory also lists CI integrations such as the CircleCI orb, the Cypress GitHub Action, Docker images, editor extensions, and Cypress Cloud features. Each of these sets up in its own way, so follow its linked docs. The npm-specific advice in this post, such as peer ranges and setupNodeEvents, applies to the npm packages.

The stage also hints at what a plugin costs to remove later. A reporter usually lives in one place, so replacing it is a configuration change. A plugin that adds commands, like a drag-and-drop helper or an inbox command for email tests, spreads into every spec that calls those commands, and replacing it means editing each of those specs.

Anthropic’s AI-Native SDLC Playbook provides a detailed blueprint for the environment where coding agents run. It builds validation directly into the loop, attempting to ensure every session checks its work before a human reviews it. But a recent Stanford study revealed a massive caveat: the exact same AI model performs 6x better when placed inside a dedicated verification harness instead of a coding harness.

As we often say about independent verification, the author of a change cannot be its verifier. An agent that wrote the code is actively rewarded for finishing it. That makes it the absolute worst candidate to decide if the code is safe to ship.

This post breaks down the testing harness that makes independent verification possible. We will look at the environment a single testing agent requires, and the platform needed to run these agents across an enterprise.

The limits of the coding harness

You might argue that the Anthropic playbook already handles bias by spinning up a verifier subagent in a fresh context. The catch is that this subagent still grades the work against the coding agent's own plan. The playbook’s evaluations test the agent's configuration rather than the actual application. These checks ensure the agent follows instructions, but they fail to confirm if the product actually works for a user.

The playbook also prevents the coding agent from approving its own pull request. That separates authorship from approval, but it skips verification. The human pressing approve still relies entirely on evidence generated by the coding harness.

True independent verification requires completely separate infrastructure, memory, and incentives.

What makes a testing agent different

Every agent operates within a harness that defines its rewards, context, toolset, memory, and fallback behaviors. You can run a coding agent and a testing agent on the identical underlying model. The harness itself determines why the testing agent catches the critical failures the coding agent glosses over.

Incentives and rewards

A coding agent wants to cross the finish line. The playbook’s verification block tells the agent to run the build, run the tests, fix any failures, and report success. Because its goal is completion, it interprets ambiguity favorably. To a coding agent trying to close a ticket, a three-second lag on the payment screen is acceptable.

A testing agent exists to find failures before your users do. It actively flags that three-second lag, captures the evidence, and hands it to a human to decide if it matters. The playbook acknowledges this inherent incentive flaw by recommending a hook that blocks coding agents from editing test files. A proper testing harness builds around this adversarial assumption from day one.

Context and worldview

Coding agents rely on repository files for commands, architecture, and team conventions. Verifying an application requires a totally different worldview. A testing harness needs deep quality context:

Behavioral models: An understanding of user workflows, states, and rules learned from real production runs.

External updates: Mechanisms to update its understanding from live telemetry and test runs to spot silent behavioral drift.

Out-of-repo knowledge: Context on third-party APIs, single sign-on (SSO) providers, and downstream services that change without a visible commit.

Explicit QA standards: The unwritten rules translated into explicit directives, such as exact-match assertions for legal compliance.

Precision retrieval: Giving the agent exactly the context it needs for the specific flow.
