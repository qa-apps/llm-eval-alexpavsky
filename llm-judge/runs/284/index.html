Polar Peaks: A journey to map the human brain

In the first two quests, students tackle flood forecasting and eye disease detection, inspired by Google Research’s Flood Forecasting initiative and AI model for diabetic retinopathy screening. Our newest quest, “Polar Peaks,” has students travel to the frontiers of neuroscience and see how AI can speed up scientific research.

With the guidance of in-game mentors, students scan and map the neurons in the brain to better understand the game character’s memory loss. They complete tasks like data cleaning and model testing, learning firsthand that AI requires careful human oversight and critical thinking.

The quest is inspired by over a decade of our research in connectomics: the science of mapping neural networks in the brain. Upon completion of the quest, students hear from two researchers behind our real-world breakthroughs, including the recent mapping of the complete fruit fly brain, the largest brain map by number of neurons to date.

Training modules: Tools for teaching AI literacy

Teachers play a critical role in bringing the quests to life and fitting them into their existing classroom curriculum. We’re rolling out new dedicated teacher training modules to help educators reinforce key AI literacy concepts and use AI Quests for learning and discussion. These are launching within the Google AI Educator Series. The modules for Quest #1 and #2 are accessible here. The training module for Quest #3 will follow next month.

Earlier this year, AI Quests won a 2026 Webby Award for AI Education, Learning & Training, and Best Global K–12 Learning Solution at the ETIH Innovation Awards. We’ll continue working with educators and partners to bring more quests to more classrooms this school year.

Your orders service calls the payment service. The payment team renames a response field and merges. Every unit test stays green and the integration suite reports the failure later. A study in the Journal of Systems and Software names poor communication of API changes as a core challenge of microservice teams. This contract testing vs integration testing guide compares both testing approaches for API and microservices teams and shows where both results belong. Keep on reading to discover key differences between contract testing and integration testing.

What Is the Difference: Contract Testing vs Integration Testing?

Contract testing checks that a consumer and a provider agree on the request and response format, with each side tested alone. Integration testing runs multiple components together with real dependencies. The two test types answer different questions:

A contract test asks whether the payment service sends the fields that the orders service reads.
An integration test asks whether the orders service and the payment service work together with the database in a real flow.

You need both answers before a release, and the table shows how contract testing compares to integration testing.

Aspect	Contract testing	Integration testing
Scope	The agreement of a consumer and a provider	Several components in a real flow
What runs	Each side alone, with a mock of the other side	All components together
Dependencies	A contract file replaces the other service	Real database and real services
Speed	Seconds, like a unit suite	Minutes, with a running environment
Who writes it	The consumer team and the provider team	Developers and QA engineers
A failure shows	A changed field or a changed status code	Wrong data or a timeout
Environment	A single service and a mock	A full test environment
CI stage	Every pull request of both services	After the merge and on a schedule

The contract test vs integration test question has a short answer: a contract test protects the API agreement, and an integration test protects the real behavior in a test environment that mirrors production. The next sections explain each way of testing and show which failures each type catches.

What Is Contract Testing?

Contract testing is a testing approach that checks that a service consumer and a service provider agree on their API. The contract is a predefined file with the expected request and response pairs. The consumer is the API client that sends requests, for example the orders service. The provider is the service that answers, for example the payment service. The Pact documentation describes contract testing as “testing an integration point by checking each application in isolation”.

Each side works in isolation and reads the same contract file, so independent services can deploy at different times and development teams avoid compatibility issues at release time. Automated contract testing works well for REST APIs, and contract testing can also cover message queues. The contract covers only the fields the consumer reads. The provider can add new fields, and the contract test stays green. The provider renames or removes a field the consumer reads, and the contract test fails in the pull request of the provider. This early detection prevents integration failures that an end-to-end test would report days later.

What is an agentic development tech stack? It's the set of systems that help AI agents complete software work safely and reliably.

The stack can include AI models, orchestration, tools, memory, guardrails, observability, evaluations, and testing.

Together, these layers help AI agents plan work, modify code, use development tools, and respond to feedback.

They also give your team control over access, risk, approvals, verification, and release decisions. Those controls become more important as agentic development changes how code is created, reviewed, tested, and released.

Models and prompts may start the process. Production use depends on the systems surrounding them.

An agentic testing platform brings independent verification into the stack from the beginning.

Why Build an Agentic Development Tech Stack?

Coding assistants can suggest functions, explain errors, or generate small changes.

Agentic workflows handle longer sequences of work throughout the delivery process.

An agent may read a ticket, inspect several files, call tools, run checks, and prepare a pull request. Each step depends on reliable context, controlled access, and clear feedback.

Without a defined stack, those responsibilities often become scattered across separate tools and team-owned integrations:

Permissions may vary
Context can get lost
Actions become harder to trace
Testing may arrive too late

An agentic development tech stack brings those systems into one operating model. It connects the tools agents use with the controls, evidence, and quality checks your team needs.

Once agents can modify code or trigger delivery systems, teams need clear approval paths and reliable verification. They also need a record of what changed, what the agent did, and how the outcome was validated.

A well-designed stack gives you consistent control across the workflow. You can limit higher-risk actions, route decisions for approval, and verify outcomes before release.
