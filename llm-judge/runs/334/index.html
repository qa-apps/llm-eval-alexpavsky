Introducing Tool Retrieval in the Gemini API
November 19, 2026
4 min read

Today we're launching Tool Retrieval in the Gemini API, available in preview in the Interactions API.

When an agent connects to dozens or even hundreds of tools, sending every full parameter schema on every request adds up fast. It inflates input token counts, adds latency, and lowers tool-selection accuracy as the candidate list grows. Tool Retrieval lets your agent keep its full tool library on standby and load parameter schemas only when the current task needs them.

How it works

To turn on Tool Retrieval, add a tool_search tool to your request and set defer_loading: true on the tools you want to hold back. The model still sees the name and description of every deferred tool, so it knows what's available, but the parameter schemas stay out of context. When the model needs a tool, it asks for it by name, the API loads the full schema, and the model calls the function, all inside the same request.

from google import genai

client = genai.Client()

tools = [
   {"type": "tool_search"},
   {
       "type": "function",
       "name": "issue_refund",
       "description": "Refund an order to the original payment method.",
       "defer_loading": True,
       "parameters": {
           "type": "object",
           "properties": {
               "order_id": {"type": "string"},
               "amount": {"type": "number"},
           },
           "required": ["order_id", "amount"],
       },
   },
   # ... 50+ other deferred functions (leave frequent tools undeferred)
]

interaction = client.interactions.create(
   model="gemini-4-hydrogen",
   input="Order A-1042 arrived damaged. Please refund 40 dollars.",
   tools=tools,
)

Inside that single API call, the model searches for issue_refund, the API loads its schema, and the model emits the function_call. All three steps appear in interaction.steps, making it easy to inspect which tools the model considered when debugging tool names or descriptions:

"steps": [
 {
   "type": "tool_search_call",
   "id": "tsc_7f2a",
   "arguments": {"function_names": ["issue_refund"]},
   "signature": "..."
 },
 {
   "type": "tool_search_result",
   "call_id": "tsc_7f2a",
   "result": [{"type": "function", "name": "issue_refund", "parameters": {...}}],
   "signature": "..."
 },
 {
   "type": "function_call",
   "id": "fc_91c3",
   "name": "issue_refund",
   "arguments": {"order_id": "A-1042", "amount": 40}
 }
]

From here it's normal function calling: your code runs the refund and sends back a function_result.

There's no index to build or host. Gemini runs the search on the server, so the only changes to your code are the new tool and a flag on the tools you want to defer. You can keep your most-used tools loaded up front and defer the long tail.

Tool Retrieval also plays well with prefix caching. Deferred schemas stay out of the start of the prompt, and the schemas the model loads are added later in the conversation, so the cached prefix stays the same from turn to turn.

Tool Retrieval also works with remote MCP servers in the Gemini API. Set defer_loading: true on an mcp_server tool and every tool that server exposes is loaded on demand, so you can connect a large server without listing its tools one by one.

How client-side retrieval works

If you maintain your own tool registry, embedding index, or per-user permission filter, declare the tool_search with "execution": "client" and define your search parameters. Client-side retrieval adds one round trip per search, because your app runs the lookup. Tools do not need to be declared upfront, so you can also expose new tools mid-conversation when a user connects an integration:

tools = [{
    "type": "tool_search",
    "execution": "client",
    "name": "search_tools",
    "description": "Search the internal tool registry for functions.",

Predictive test analytics helps you estimate which tests will likely fail and how risky your next release is. It combines historical data from your test runs with current data from code changes. You don’t need to buy test data for predictive analytics. Your CI pipeline already saves most of it for free. After each run you get a pass rate and a list of failed tests. These numbers describe the past. On release day you need answers about the next build: is it safe to release, and which tests should you run first? You can add a model later. What Is Predictive Test Analytics?

Predictive test analytics is the practice of using past test results to estimate future test outcomes and release risk. It is a part of data analytics. Predictive analytics is the use of statistical methods and machine learning techniques to predict future outcomes based on historical data. In business analytics, banks use it to measure credit risk, and factories use it for predictive maintenance.

In QA, you apply the same techniques to predict test failures and release risk. With classic test automation reporting, you see runs that have finished. With predictive analytics, you take the same data and estimate the next run. So you don’t need new data sources to start. You need a longer and cleaner history. Meta deployed this approach in production. Its research team presented a predictive test selection system and described the method in a research paper. You can read about the statistical models in our guide on predictive analytics in QA.

Analysts expect fast adoption of AI in testing. Gartner predicts in its Market Guide for AI-Augmented Software-Testing Tools that 80% of enterprises will use these tools by 2027, while the share was about 15% in early 2023.

Types Of Predictive Models For Test Data

A predictive model learns from data from the past and gives you an output, such as a risk score for each test. Common types of predictive models for test data are:

Regression models and decision trees, mathematical and statistical models that work with smaller data sets.
Neural networks and other deep learning methods, which need very large amounts of data and fit companies with big data in CI.

Model building is a part of the analysis process, and it starts with data preparation. You remove flaky failures from the run history and split the dataset into subsets for training and for testing the model. In the training data, each test run is a data point with a set of features, such as:

Changed files
Test type
Past failures
Duration

Some features are categorical, for example the test framework. The model converts them into a vector of numbers.

Run history is also time series data, because each result has a date. Using data like this, machine learning algorithms find patterns in large data sets. In data science, this process is close to data mining. The output of this predictive analysis is a ranked list of tests.

Autonomous testing readiness varies by task. A team may automate execution safely while keeping test creation or maintenance under review.

Approval rules, ownership, escalation paths, and traceable evidence determine how much authority each testing activity should receive.
Expansion should follow measurable gains in signal quality, maintenance effort, and release confidence. Test volume alone reveals little about readiness.

An autonomous testing pilot can look successful within days. Test generation often delivers the first visible win, allowing teams to create coverage quickly from requirements or plain-language prompts.

The harder work begins as that coverage grows. Tests must remain reliable through application changes, shifting environments, and ambiguous failures. An unclear recovery or false release signal then raises a more consequential question: Which decisions can the system make on its own?

Autonomous testing can reduce substantial operational work across QA. Safe expansion depends on the standards, access, evidence, and accountability surrounding it.

This guide explores the foundations teams need before expanding AI-driven QA across applications and delivery pipelines.

What Is Autonomous Testing?

Autonomous testing uses AI to perform selected software testing activities with limited supervision. Those activities can include creating tests, choosing what to run, executing tests, analyzing failures, and maintaining coverage as an application changes.

Traditional test automation follows predefined scripts and rules. Autonomous testing can interpret goals, use application context, and determine the next action within set boundaries. A team still defines those boundaries and decides which actions require approval.

Agentic testing and autonomous testing are closely related. Agentic testing describes how goal-directed AI systems plan and complete testing work. Autonomy describes the authority those systems receive. An agent can assist with a task, recommend an action, or complete it automatically.
